# Tesselot - アーキテクチャ

## はじめに

Tesselotは、ロウポリ画像を作るブラウザエディターです。ユーザーは画像の上にガイド図形（**モディファイア**：直線、曲線、円）を描き、アプリケーションが残りの空間に点を撒いて三角形分割し、色を塗ります。ユーザーにとって何ができるかはREADMEを参照してください。このドキュメントはコードの構造についてのものです。

コードを読む前に理解しておくべき最も重要な点：このパイプラインは完全に非破壊的です。状態は厳密に**source**（ユーザーが指定したもの - 画像、設定、図形ツリー）と**derived**（点、三角形分割、色）に分かれています。保存され、履歴に残るのはsourceだけです。derivedは変更のたびに、また読み込みのたびにsourceから再計算され、決して保存されません。

この分離から、残りのアーキテクチャのほとんどすべてが導かれます。undoは軽量です（スナップショットはsourceのみ）。すべてが決定的です（同じsourceは常に同じderivedを生成します）。重い計算はバックグラウンドに追い出されています（derivedの計算は重いため）。そしてデータは常に一方向、sourceからderivedへ流れ、決して逆には流れません。

馴染みのある例で言えば、これはRedux/Flux的な単方向データフロー - 単一の状態、コマンドを通じてのみ変更、購読者がイベントに反応する - に、computed/reselectのような計算済み状態のレイヤーを重ねたものに似ています。

## 5つのレイヤー

| レイヤー | フォルダ | 責務 | 何を知っているか |
|---|---|---|---|
| **UI** | `src/ui/` | 入力：描画、パネル、ツール、ホットキー | モデル（コマンドを送る） |
| **モデル** | `src/document/` | source + derived、履歴、イベント | 自分より上位は何も知らない |
| **ドメイン** | `src/domain/` | 純粋なロジック：図形がどう点に変換されるか、WASMへの橋渡し | モデルから呼ばれる |
| **レンダー** | `src/preview/` | three.jsで画像と三角形を描画 | モデルを読むだけ |
| **ネイティブ** | `crates/` | Rust->WASM：重い幾何計算と色計算 | 何も知らない、純粋関数 |

補助的なフォルダもいくつかあります：`persistence/`（保存とエクスポート）、`settings/`、`i18n/`。

フローのルール：UIはモデルだけを変更し、レンダーはモデルを読むだけで、両者が直接やり取りすることはありません。両者をつなぐのはモデル内部のイベントバスで、これが単方向サイクルを構成しています。

## データフロー

主なシナリオは「マウスの一筆から、色が塗り直された三角形まで」です。

```
   ユーザー           (1) UIが入力を捕捉
       |
       v
   (2) コマンドがSOURCEを変更：図形を追加/移動
       |
       v
   (3) 再計算：source -> 点 -> 三角形      [重い処理、バックグラウンドワーカーで実行]
       |
       v
   (4) モデルが結果をフラットバッファに格納し、「完了」イベントを送出
       |
       v
   (5) レンダーがイベントを受け取り、画面の画像を更新
       |
       +--> (6) 並行して三角形の色を計算 -> 別のイベント -> 塗り直し
```

このサイクルを軽快にしているのは3つの工夫です。

- **1フレームにつき1回の再計算。** ドラッグ中はマウスイベントが1秒間に何十回も発生しますが、再計算は1フレームに1回までしか実行されません - 途中の位置は破棄されます。
- **レンダーは決して待たない。** バックグラウンドで正確な色が計算されている間も、三角形はすぐに近似色で表示されます。正確な色は別のイベントとして届き、その上に重ねられます。
- **余分なアロケーションをしない。** 三角形はオブジェクトとしてではなく、長いフラットな数値配列として存在します。レンダーもエクスポートも、これらの配列を直接読み取ります。

## レイヤーごとの詳細

### モデル（`src/document/`）

状態は単一のオブジェクト `DocumentData`（`types.ts`）で、ちょうどこの境界で分かれています。

- **Source**（保存され、履歴に残る）：`image`、`seed`、`seedSettings`、`colorSettings`、`stack`（図形ツリー）。
- **Derived**（再計算され、保存されない）：`points`とフラットなレンダーバッファ - `renderPositions`（頂点ごとのxyz）、`renderColors`（三角形ごとのrgb）、`triangleCount`。

変更がモデルをどう通過するか：

- `store.ts` - 単一の可変な状態オブジェクト（`store.data()`）。
- `commands/` - それを変更する唯一の手段で、reducersに相当します。コマンドはsourceをその場で書き換え、コミットを呼び出します：`commit.ts`が再計算が必要か（`commitStructural`、ジオメトリの編集用）、履歴のステップを記録するだけで十分か（`commitViewOnly`、例えばフォルダを折りたたむ場合）を判断します。
- `commands/pipeline.ts` - 再計算（`evaluatePoints`）。「同時進行は1件まで」の原則で動作します：どれだけ編集が来ても、ワーカーに同時に送られる計算は1件だけですが、最後の計算は必ず最後まで実行されます。
- `commands/recompute.ts` - 結果をフラットバッファに展開する（`buildGeometry`）ことと、計算済みの色を適用する（`applyColorGrid`）こと。
- `signals.ts` - イベントバス（`ferrsign`ベース）。モデルは何も描画しません。「点が変わった」「三角形が変わった」「sourceがまるごと置き換わった」を伝えるだけで、レンダー、パネル、履歴といった購読者がそれに反応します。
- `history.ts` - undo/redo。スナップショットはsourceのみ（画像すら含みません）なので軽量です。ドラッグのジェスチャー全体が1つの履歴ステップに畳み込まれます。
- `selectors/` - モデルの外部への読み取り経路。コマンドを介さずに誰かが状態を壊さないよう、クローンを返します。例外はフラットバッファで、速度のため参照で返されます。

図形ツリー（`stack`）は、Blenderのコレクションのように1階層です：要素は独立した図形か、子を持つグループのどちらかです。グループには「折りたたむ」（表示のみ）と「ミュート」（計算から除外）があります。スタック内の順序には意味があります。ツリーに対する構造的な操作は`commands/stackTree.ts`、`modifierCommands.ts`、`groupCommands.ts`にあります。

### ドメイン（`src/domain/`）

DOMとthree.jsに依存しないロジックです。唯一の例外は`imageSource.ts`で、これは`<canvas>`からピクセルを読み取ります。2つのサブテーマがあります：

- `modifiers/` - 各図形が点と拘束エッジ（`ModifierResult`）にどう変換されるか：`path.ts`（折れ線またはCatmull-Romスプライン）、`bezier.ts`（対称ハンドル付きのベジェ曲線）、`circle.ts`。共通の集約は`result.ts`です。
- ネイティブレイヤーへの橋渡し：各WASM crateには「ファサード + ワーカー + クライアント」の三つ組があります。重い計算はWeb Workerで行われ、データはtransferable配列としてコピーなしで境界を越えます。

その他細かい点：`rng.ts`（決定的な擬似乱数生成器）、`colorGrid.ts`（色の空間検索）、`groupColor.ts`（グループの色はその名前から導出されます - 名前を変えれば色も変わります）。

### レンダー（`src/preview/`）

モデルのイベントを厳密に一方向にのみ聞き取り、モデルへの逆参照はありません。ワールド座標は画像の座標と一致し（Y軸下向き）、カメラは正投影です。

- `preview.ts` - コーディネーター：1つのシーン、1つのレンダラー、複数のレイヤー。
- 各レイヤーは自分のthree.jsオブジェクトを所有します：`triangleLayer.ts`（三角形。バッファを毎フレーム再生成せず使い回します）、`imageLayer.ts`（元画像）、`pointLayer.ts`（種となる点）、`overlayLayer.ts`（編集用オーバーレイ：選択、ハンドル、ドラフト）。
- `receiving.ts` - 「モデルのイベント -> レイヤー呼び出し」の橋渡し。ここで最適化も行われます：「塗り直し」イベントでは色だけが更新され、「再構築」イベントでは位置と色の両方が更新されます。
- `viewport.ts` - カメラと画面<->画像座標の変換（ズーム、パン）。

### UI（`src/ui/`）

フレームワークを使わない命令的なDOM/canvasです。パネルはイベントを受けて自分のDOMを再構築します。UIの状態を直接変更することは決してなく、常にコマンドを経由します。

- `tools.ts`（`ToolController`）- 「選択 / 描画 / ドラッグ」モードのステートマシン。キャンバス上の入力を捕捉します。
- `tools/` - ツールの実装：描画中の図形のドラフト（`*Draft.ts`）と、点のドラッグを扱う`dragSession.ts`。ここに「1フレームにつき1回の再計算」とジェスチャーを1つのundoステップに畳み込む処理があります。
- `panel/` - 右側のパネル：グループとドラッグアンドドロップ付きの図形ツリー（`stackView.ts`、`dnd.ts`）。
- その他：ツールパレット、選択とハイライト、ホットキー、トースト通知。

### ネイティブレイヤー（`crates/`）

独立した2つのcrateがあり、それぞれ読み込んだ画像を自分でキャッシュし、呼び出しのたびに転送せずに済むようにしています。

- `crates/pipeline/` - 幾何計算：`sobel.rs`（画像のエッジに基づく密度マップ。変化が急なところほど点が密になります）、`seeding.rs`（可変半径のBridson法による点の配置）、`triangulate.rs`（制約付きドロネー三角形分割、`spade` crate）、`contours.rs`（画像の輪郭を編集可能な図形にトレースする、Cannyアルゴリズム）。
- `crates/color/` - 色：各三角形の下の色（平均または中央値）をサンプリングし、高速検索のための空間グリッドを構築します。色計算用ワーカー内で動作します。

決定性にとって重要な部分 - 擬似乱数生成器、点の配置、サンプリング - は、以前のTS実装とビット単位で意図的に一致させてあります。同じseedは、どの実行環境でも同じ画像を生成します。

## ビルド

- `npm run build:wasm` - 各crateについて：cargo -> wasm-bindgen（`--target web`）-> wasm-opt（`-Oz`）。生成されたグルーコードは`src/generated/`（gitignore対象）に置かれ、`.wasm`は`dist/`にコピーされて実行時に読み込まれます。
- `npm run build` = `build:wasm`のあとに`rollup -c`。`npm run dev`はwatch（`-w`）を追加します。
- デプロイは静的（GitHub Pages）で、バックエンドはありません。

## まとめ

アプリケーションが保持するのはsourceだけです。ユーザーはUIを通じてそれを編集し、モデルはバックグラウンドのRust/WASMパイプラインを通してそれをフラットバッファに変換し、レンダーはそのバッファを反映するだけです。それ以外のすべては、このたった1つの分離から導かれる帰結です。
