# Polygonize - архитектура

## Предисловие

Polygonize - браузерный редактор low-poly изображений: пользователь рисует поверх картинки направляющие фигуры (**модификаторы**: линии, кривые, окружности), а приложение засевает точками остальное пространство, триангулирует и красит. Что это даёт пользователю - в README; этот документ - про устройство кода.

Главное, что нужно понять до чтения кода: пайплайн полностью недеструктивный. Состояние жёстко разделено на **source** - то, что задал пользователь (картинка, настройки, дерево фигур), - и **derived** - точки, триангуляция, цвета. Хранится и попадает в историю только source; derived заново вычисляется из него при каждом изменении и каждой загрузке и не сохраняется никогда.

Из этого разделения следует почти вся остальная архитектура: undo дешёвый (снимок - только source), всё детерминировано (один source всегда даёт один derived), тяжёлые вычисления вынесены в фон (derived дорого считать), а данные текут строго в одну сторону - от source к derived, никогда обратно.

Из знакомого это похоже на однонаправленный поток данных Redux/Flux - единое состояние, изменения только через команды, подписчики реагируют на события - плюс слой вычисляемого состояния поверх, как computed/reselect.

## Пять слоёв

| Слой | Папка | За что отвечает | Знает про |
|---|---|---|---|
| **UI** | `src/ui/` | ввод: рисование, панель, инструменты, хоткеи | модель (шлёт команды) |
| **Модель** | `src/document/` | source + derived, история, события | ничего выше себя |
| **Домен** | `src/domain/` | чистая логика: как фигура превращается в точки, мосты к WASM | модель зовёт его |
| **Рендер** | `src/preview/` | рисует картинку и треугольники на three.js | только слушает модель |
| **Нативный** | `crates/` | Rust->WASM: тяжёлая геометрия и цвет | ничего, чистые функции |

Есть ещё несколько вспомогательных папок: `persistence/` (сохранение и экспорт), `settings/`, `i18n/`.

Правило потока: UI меняет только модель, рендер только читает модель, напрямую они не общаются. Связывает их шина событий внутри модели - это и есть однонаправленный цикл.

## Поток данных

Главный сценарий - "от штриха мыши до перекрашенных треугольников":

```
   пользователь        (1) UI ловит ввод
       |
       v
   (2) команда меняет SOURCE: добавила/сдвинула фигуру
       |
       v
   (3) пересчёт: source -> точки -> треугольники      [тяжёлое, в фоновом воркере]
       |
       v
   (4) модель кладёт результат в плоские буферы и шлёт событие "готово"
       |
       v
   (5) рендер слышит событие и обновляет картинку на экране
       |
       +--> (6) параллельно считается цвет треугольников -> ещё одно событие -> перекраска
```

Отзывчивым этот цикл делают три приёма:

- **Один пересчёт на кадр.** При перетаскивании события мыши сыплются десятками в секунду, но пересчёт запускается не чаще раза за кадр - промежуточные позиции отбрасываются.
- **Рендер никогда не ждёт.** Пока в фоне считается точный цвет, треугольники сразу показываются с приблизительным; готовый цвет прилетает отдельным событием и доезжает поверх.
- **Никаких лишних аллокаций.** Треугольники живут не как объекты, а как длинные плоские массивы чисел; и рендер, и экспорт читают эти массивы напрямую.

## Карта задач

| Хочу изменить... | Смотрю в... |
|---|---|
| поведение инструментов рисования | `src/ui/tools/` |
| правую панель (дерево фигур, группы) | `src/ui/panel/` |
| как фигура превращается в точки | `src/domain/modifiers/` |
| алгоритм посева точек / триангуляцию | `crates/pipeline/` |
| как считается цвет треугольника | `crates/color/` |

| сохранение на диск / экспорт SVG, PDF, PNG | `src/persistence/` |

## Детали по слоям

### Модель (`src/document/`)

Состояние - один объект `DocumentData` (`types.ts`), разделённый ровно по этой границе:

- **Source** (сохраняется, есть в истории): `image`, `seed`, `seedSettings`, `colorSettings`, `stack` (дерево фигур).
- **Derived** (пересчитывается, не сохраняется): `points` и плоские буферы рендера - `renderPositions` (xyz на вершину), `renderColors` (rgb на треугольник), `triangleCount`.

Как изменение проходит через модель:

- `store.ts` - единый мутируемый объект состояния (`store.data()`).
- `commands/` - единственный способ его менять, аналог reducers. Команда правит source на месте и вызывает коммит: `commit.ts` решает, нужен ли пересчёт (`commitStructural` для правок геометрии) или достаточно записать шаг истории (`commitViewOnly`, например свернуть папку).
- `commands/pipeline.ts` - пересчёт (`evaluatePoints`). Работает по принципу "один запрос в полёте": сколько бы правок ни пришло, к воркеру одновременно идёт только один расчёт, но последний всегда доводится до конца.
- `commands/recompute.ts` - раскладка результата в плоские буферы (`buildGeometry`) и применение посчитанного цвета (`applyColorGrid`).
- `signals.ts` - шина событий (на `ferrsign`). Модель ничего не рендерит; она лишь сообщает "точки поменялись", "треугольники поменялись", "источник заменён целиком", а подписчики - рендер, панель, история - реагируют.
- `history.ts` - undo/redo. Снимок - это только source, даже без картинки, поэтому дешёвый; целый жест перетаскивания схлопывается в один шаг.
- `selectors/` - чтение модели наружу. Отдаёт клоны, чтобы никто не портил состояние мимо команд; исключение - плоские буферы, их отдают по ссылке ради скорости.

Дерево фигур (`stack`) одноуровневое, как коллекции в Blender: элемент - либо свободная фигура, либо группа с детьми. У группы есть "свернуть" (только вид) и "заглушить" (исключить из расчёта). Порядок в стеке значим. Структурные операции над деревом - `commands/stackTree.ts`, `modifierCommands.ts`, `groupCommands.ts`.

### Домен (`src/domain/`)

Логика без DOM и three.js; единственное исключение - `imageSource.ts`, который читает пиксели с `<canvas>`. Две подтемы:

- `modifiers/` - как каждая фигура превращается в точки и рёбра-ограничения (`ModifierResult`): `path.ts` (ломаная или сплайн Катмулла-Рома), `bezier.ts` (кривая Безье с симметричными ручками), `circle.ts`. Общий сборщик - `result.ts`.
- Мосты к нативному слою: для каждого WASM-crate есть тройка "фасад + воркер + клиент". Тяжёлые вычисления идут в Web Workers, данные пересекают границу как transferable-массивы, без копирования.

Мелочи: `rng.ts` (детерминированный ГПСЧ), `colorGrid.ts` (пространственный поиск цвета), `groupColor.ts` (цвет группы выводится из её имени - переименовал, значит перекрасил).

### Рендер (`src/preview/`)

Слушает события модели строго в одну сторону, обратной ссылки в модель нет. Координаты мира совпадают с координатами картинки (Y вниз), камера ортографическая.

- `preview.ts` - координатор: одна сцена, один рендерер, набор слоёв.
- Слои владеют своими three.js-объектами: `triangleLayer.ts` (треугольники; переиспользует буферы, а не пересоздаёт каждый кадр), `imageLayer.ts` (исходная картинка), `pointLayer.ts` (точки посева), `overlayLayer.ts` (оверлеи редактирования: выделение, ручки, черновик).
- `receiving.ts` - мост "события модели -> вызовы слоёв". Здесь же оптимизация: на событие "перекрашено" обновляются только цвета, на "перестроено" - и позиции, и цвета.
- `viewport.ts` - камера и пересчёт координат экран<->картинка (зум, панорама).

### UI (`src/ui/`)

Императивный DOM/canvas без фреймворка; панели перестраивают свой DOM по событию. Состояние UI никогда не меняет напрямую - только через команды.

- `tools.ts` (`ToolController`) - конечный автомат по режимам "выбор / рисование / перетаскивание"; ловит ввод на холсте.
- `tools/` - реализация инструментов: черновики рисуемых фигур (`*Draft.ts`) и `dragSession.ts` - перетаскивание точки; здесь живут "один пересчёт на кадр" и схлопывание жеста в один шаг undo.
- `panel/` - правая панель: дерево фигур с группами и drag-and-drop (`stackView.ts`, `dnd.ts`).
- Остальное - палитра инструментов, выделение и подсветка, хоткеи, тосты.

### Нативный слой (`crates/`)

Два независимых crate; каждый кэширует загруженную картинку у себя, чтобы не пересылать её на каждый вызов.

- `crates/pipeline/` - геометрия: `sobel.rs` (карта плотности по краям картинки: где резкий перепад, там точки гуще), `seeding.rs` (расстановка точек методом Бридсона с переменным радиусом), `triangulate.rs` (триангуляция Делоне с ограничениями, crate `spade`), `contours.rs` (трассировка контуров картинки в редактируемые фигуры, Canny).
- `crates/color/` - цвет: семплирует цвет под каждым треугольником (среднее или медиана) и строит пространственную сетку для быстрого поиска. Работает в цветовом воркере.

Части, критичные для детерминизма - ГПСЧ, посев, семплирование - намеренно совпадают с бывшей TS-реализацией бит-в-бит: один seed даёт одну и ту же картинку на любом запуске.

## Сборка

- `npm run build:wasm` - для каждого crate: cargo -> wasm-bindgen (`--target web`) -> wasm-opt (`-Oz`). Склейка кладётся в `src/generated/` (в gitignore), `.wasm` копируется в `dist/` и грузится в рантайме.
- `npm run build` = `build:wasm`, затем `rollup -c`. `npm run dev` добавляет watch (`-w`).
- Деплой статический (GitHub Pages), без бэкенда.

## Итог

Приложение хранит только source: пользователь правит его через UI, модель гоняет его через фоновый Rust/WASM-пайплайн в плоские буферы, а рендер лишь отражает эти буферы. Всё остальное - следствия этого одного разделения.
