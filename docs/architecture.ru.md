# Polygonize - архитектура (онбординг)

Этот документ устроен как дерево: сверху ствол (что за приложение и одна главная идея),
ниже - крупные ветки (цикл данных, слои), и только в глубине - конкретные модули и файлы.
Читайте сверху вниз и останавливайтесь там, где стало достаточно: после раздела 1 у вас
есть общая картина, после раздела 3 - рабочая модель происходящего, дальше - детали по
необходимости. Не нужно держать в голове всё сразу.

---

## 1. Ствол: что это и одна главная идея

**Что делает приложение.** Polygonize - браузерный редактор, который превращает картинку в
низкополигональный "витраж": поле треугольников, где каждый треугольник закрашен усреднённым
цветом пикселей под ним. Пользователь не расставляет точки руками - он рисует поверх картинки
направляющие фигуры (их называют **модификаторы**: линии, кривые, окружности), а приложение
само засевает точками остальное пространство, триангулирует и красит.

**Одна главная идея, без которой ничего не понятно: приложение процедурное.** Оно хранит не
результат, а *рецепт* результата. Сохраняется только то, что задал пользователь (картинка,
настройки, нарисованные фигуры). Сама триангуляция - тысячи точек и треугольников - нигде не
хранится: она заново вычисляется из рецепта при каждом изменении и при каждой загрузке.

Держите в голове аналогию "рецепт против блюда":

- **Рецепт (source)** - маленький, его и сохраняем, по нему работает undo.
- **Блюдо (derived)** - большое, каждый раз готовится заново, никогда не сохраняется.

Из этой одной идеи вытекает почти вся остальная архитектура: почему undo дешёвый (хранит
рецепт, а не блюдо), почему всё детерминировано (один рецепт всегда даёт одно блюдо), почему
тяжёлые вычисления вынесены в фон (готовка блюда - дорогая) и почему данные текут строго в
одну сторону (от рецепта к блюду, никогда обратно).

**На что это похоже из знакомого.** Однонаправленный поток данных как в Redux/Flux (единое
состояние, изменения только через "команды", подписчики реагируют на события) плюс слой
вычисляемого состояния поверх (как computed/reselect: source -> чистая функция -> результат).

## 2. Первая ветвь: пять слоёв

Код делится на пять слоёв. Пока просто запомните, кто за что отвечает и в какую сторону
смотрит - детали каждого будут ниже.

| Слой | Папка | За что отвечает | Знает про |
|---|---|---|---|
| **UI** | `src/ui/` | ввод: рисование, панель, инструменты, хоткеи | модель (шлёт команды) |
| **Модель** | `src/document/` | рецепт + производное состояние, история, события | ничего выше себя |
| **Домен** | `src/domain/` | чистая логика: как фигура превращается в точки, мосты к WASM | модель зовёт его |
| **Рендер** | `src/preview/` | рисует картинку и треугольники на three.js | только слушает модель |
| **Нативный** | `crates/` | Rust->WASM: тяжёлая геометрия и цвет | ничего, чистые функции |

Плюс несколько вспомогательных: `persistence/` (сохранение и экспорт), `settings/`
(настройки), `i18n/` (локализация).

Ключевое правило потока: **UI меняет только модель; рендер только читает модель; напрямую
UI и рендер не общаются.** Их связывает шина событий внутри модели. Это и есть тот самый
однонаправленный цикл.

---

## 3. Вторая ветвь: как течёт поток данных

Это главный сценарий работы приложения - "от штриха мыши до перекрашенных треугольников".
Опишем его как замкнутый цикл; детали каждого шага раскрываются в разделе 5.

```
   пользователь        (1) UI ловит ввод
       |
       v
   (2) команда меняет РЕЦЕПТ (source): добавила/сдвинула фигуру
       |
       v
   (3) пересчёт: рецепт -> точки -> треугольники      [тяжёлое, в фоновом воркере]
       |
       v
   (4) модель кладёт результат в плоские буферы и шлёт событие "готово"
       |
       v
   (5) рендер слышит событие и обновляет картинку на экране
       |
       +--> (6) параллельно считается цвет треугольников -> ещё одно событие -> перекраска
```

Три вещи, которые делают этот цикл быстрым и отзывчивым (все три - следствие "процедурной"
идеи из раздела 1):

- **Один пересчёт на кадр.** Во время перетаскивания события мыши сыплются десятками в
  секунду, но пересчёт запускается не чаще одного раза за кадр экрана - лишние промежуточные
  позиции отбрасываются.
- **Рендер никогда не ждёт.** Пока в фоне считается точный цвет, треугольники сразу
  показываются с приблизительным цветом. Готовый цвет прилетает отдельным событием и
  доезжает "поверх".
- **Никаких лишних аллокаций.** Треугольники живут не как объекты, а как длинные плоские
  массивы чисел; и рендер, и экспорт читают эти же массивы напрямую.

Если из всего документа запомнить только раздел 1 и эту схему - уже можно ориентироваться в
коде.

## 4. Третья ветвь: где что искать (карта задач)

Прежде чем нырять в детали, вот навигация: с какой задачей в какую ветку идти.

| Хочу изменить... | Смотрю в... |
|---|---|
| поведение инструментов рисования | `src/ui/tools/` |
| левую панель (дерево фигур, группы) | `src/ui/panel/` |
| как фигура превращается в точки | `src/domain/modifiers/` |
| алгоритм посева точек / триангуляцию | `crates/pipeline/` |
| как считается цвет треугольника | `crates/color/` |
| отрисовку, камеру, оверлеи | `src/preview/` |
| формат сохранения / undo | `src/document/` |
| сохранение на диск / экспорт SVG,PDF,PNG | `src/persistence/` |

Дальше - детали каждой ветки. Их читают точечно, под конкретную задачу, а не подряд.

## 5. Листья: детали по слоям

### 5.1. Модель (`src/document/`) - сердце

Состояние - один объект `DocumentData` (`types.ts`), разделённый ровно по идее из раздела 1:

- **Source** (сохраняется, есть в истории): `image`, `seed`, `seedSettings`,
  `colorSettings`, `stack` (дерево фигур).
- **Derived** (пересчитывается, не сохраняется): `points`, `constraintEdges` и **плоские
  буферы рендера** `renderPositions` (xyz на вершину), `renderColors` (rgb на треугольник),
  `triangleCount`.

Как течёт изменение внутри модели:

- **`store.ts`** - единый мутируемый объект состояния (`store.data()`).
- **`commands/`** - единственный способ его менять (аналог reducers). Команда правит source
  "на месте" и вызывает коммит: `commit.ts` решает, нужен ли пересчёт (`commitStructural`
  для правок геометрии) или достаточно записать шаг истории (`commitViewOnly`, например
  свернуть папку).
- **`commands/pipeline.ts`** - пересчёт (`evaluatePoints`). Устроен как "один запрос в
  полёте": сколько бы правок ни пришло, к воркеру одновременно идёт только один расчёт, но
  последний всегда доводится до конца.
- **`commands/recompute.ts`** - раскладка результата в плоские буферы (`buildGeometry`) и
  применение посчитанного цвета (`applyColorGrid`).
- **`signals.ts`** - шина событий (на `ferrsign`). Модель ничего не рендерит; она лишь
  кричит "точки поменялись", "треугольники поменялись", "источник заменён целиком", а
  подписчики (рендер, панель, история) реагируют.
- **`history.ts`** - undo/redo. Снимок - это только source (даже без картинки), поэтому
  дешёвый; целый жест перетаскивания схлопывается в один шаг.
- **`selectors/`** - чтение модели наружу; отдаёт клоны, чтобы никто не портил состояние
  мимо команд (исключение - плоские буферы, их отдают по ссылке ради скорости).

**Дерево фигур (`stack`)** - одноуровневое, как папки-коллекции в Blender: элемент это либо
свободная фигура, либо группа с детьми. У группы есть "свернуть" (только вид) и "заглушить"
(исключить из расчёта). Порядок в стеке значим. Структурные операции над деревом -
`commands/stackTree.ts`, `modifierCommands.ts`, `groupCommands.ts`.

### 5.2. Домен (`src/domain/`) - чистая логика

Логика без DOM и three.js (единственное исключение - `imageSource.ts`, читает пиксели с
`<canvas>`). Две подтемы:

- **`modifiers/`** - как каждая фигура превращается в точки и рёбра-ограничения
  (`ModifierResult`): `path.ts` (ломаная или сплайн Катмулла-Рома), `bezier.ts` (кривая
  Безье с симметричными ручками), `circle.ts`. Общий сборщик - `result.ts`.
- **Мосты к нативному слою** (см. 5.5): для каждого WASM-crate есть тройка "фасад + воркер +
  клиент". Тяжёлые вычисления идут в отдельных потоках (Web Workers), данные пересекают
  границу как передаваемые (transferable) массивы - без копирования.

Плюс мелочи: `rng.ts` (детерминированный ГПСЧ), `colorGrid.ts` (пространственный поиск
цвета), `groupColor.ts` (цвет группы выводится из её имени - переименовал, значит перекрасил).

### 5.3. Рендер (`src/preview/`) - three.js

Слушает события модели строго в одну сторону; обратной ссылки в модель нет. Координаты мира
совпадают с координатами картинки (Y вниз), камера ортографическая.

- **`preview.ts`** - координатор: одна сцена, один рендерер, набор слоёв.
- Слои владеют своими three.js-объектами: `triangleLayer.ts` (сами треугольники;
  переиспользует буферы, а не пересоздаёт их каждый кадр), `imageLayer.ts` (исходная
  картинка), `pointLayer.ts` (точки посева), `overlayLayer.ts` (оверлеи редактирования:
  выделение, ручки, черновик).
- **`receiving.ts`** - мост "события модели -> вызовы слоёв". Здесь же живёт оптимизация: на
  событие "перекрашено" обновляются только цвета, на "перестроено" - и позиции, и цвета.
- **`viewport.ts`** - камера и весь пересчёт координат экран<->картинка (зум, панорама).

### 5.4. UI (`src/ui/`) - ввод

Императивный DOM/canvas без фреймворка; панели перестраивают свой DOM по событию. Никогда не
меняет состояние напрямую - только через команды.

- **`tools.ts`** (`ToolController`) - конечный автомат по режимам "выбор / рисование /
  перетаскивание"; ловит ввод на холсте.
- **`tools/`** - реализация инструментов: "черновики" рисуемых фигур (`*Draft.ts`) и
  `dragSession.ts` (перетаскивание точки; тут и живёт "один пересчёт на кадр" из раздела 3,
  и схлопывание жеста в один undo).
- **`panel/`** - левая панель: дерево фигур с группами и drag-and-drop (`stackView.ts`,
  `dnd.ts`).
- Остальное - палитра инструментов, выделение/подсветка, хоткеи, тосты и прочая обвязка.

### 5.5. Нативный слой (`crates/`) - Rust->WASM

Два независимых crate; каждый кэширует загруженную картинку у себя, чтобы не пересылать её на
каждый вызов.

- **`crates/pipeline/`** - геометрия. `sobel.rs` (карта плотности по краям картинки:
  где резкий перепад - там точки гуще), `seeding.rs` (расстановка точек методом Бридсона с
  переменным радиусом), `triangulate.rs` (триангуляция Делоне с ограничениями через crate
  `spade`), `contours.rs` (трассировка контуров картинки в редактируемые фигуры, Canny).
- **`crates/color/`** - цвет: семплирует цвет под каждым треугольником (среднее или медиана)
  и строит пространственную сетку для быстрого поиска. Работает в цветовом воркере.

Части, критичные для детерминизма (ГПСЧ, посев, семплирование), намеренно совпадают с бывшей
TS-реализацией бит-в-бит: один seed - одна картинка на любом запуске.

## 6. Сборка

- `npm run build:wasm` - для каждого crate: cargo -> wasm-bindgen (`--target web`) ->
  wasm-opt (`-Oz`). Склейка кладётся в `src/generated/` (в gitignore), `.wasm` копируется в
  `dist/` и грузится в рантайме.
- `npm run build` = `build:wasm`, затем `rollup -c`. `npm run dev` добавляет watch (`-w`).
- Деплой статический (GitHub Pages), без бэкенда.

---

## 7. Итог одной фразой

Приложение хранит рецепт, а не блюдо: пользователь правит рецепт через UI, модель гоняет его
через фоновый Rust/WASM-пайплайн в плоские буферы, а рендер лишь отражает эти буферы. Всё
остальное - следствия этой одной идеи.
